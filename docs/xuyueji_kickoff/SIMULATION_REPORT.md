# 架构推演报告：从一个用户发消息到最终结算

> 本文是**设计级桌面推演**：依据设计契约检验异常路径，不是已运行的生产压测或经过真实支付检验的代码。

## 固定测试环境

- 用户 A：有 20,000 积分、长剧情会话 C，当前分支 head=H10、branch revision=17。
- 用户 A 的手机与 PC 同时在线；PC 在编辑角色卡 rev=8，手机仍缓存 rev=7。
- 世界书 W 中存在递归关系 A→B→A；宏有随机选项，随机数种子由 run_id 确定。
- DeepSeek Flash/Pro 按其最新官方 price / usage 表计费；安全级别由服务端强制 high。
- 单台 2C/2GiB、40GiB、3Mbps ECS；正常情况下 API 生成 600~2000 Token，不宣称真实性能已测。

## S1：常规剧情生成（成功路径）

| 时点 | 事件                          | 必须发生的状态转移                                          |
| ---- | ----------------------------- | ----------------------------------------------------------- |
| t0   | 用户在浏览器按「发送」        | 草稿被写入本地 outbox，显示同步中                           |
| t1   | 服务端确认该消息和分支 rev=17 | 保存不可变用户节点 U11、branch rev=18                       |
| t2   | 客户端提交生成指令 + 幂等 key | 创建 generation_run R1，不直接扣正式费用                    |
| t3   | 服务端冻结最高积分并快照版本  | R1=reserved；钱包 available 减少、reserved 增加；短事务提交 |
| t4   | 编译世界书+记忆+会话路径      | PromptTrace 包含命中来源、预算与版本摘要                    |
| t5   | 上游流式输出                  | 浏览器仅显示临时 token，服务端记录运行状态                  |
| t6   | 最终安全通过 + usage 到达     | 结算账本、正式保存 AI 节点 A12、branch rev=19、释放未用冻结 |
| t7   | PC/手机同步游标更新           | 两端展示同一条 AI 回复与一致的已结算积分                    |

**不变量**：R1 最多一次最终结算；A12 在成功安全终态前不是正式消息；历史模型输入与世界书/角色版本可追溯。

## S2：世界书环与两设备修改人设

PC 将角色卡更新至 rev=8，手机正在发送消息且仍持有 rev=7：

- 手机若提交基于旧版本的改动：返回 409 并保留草稿，不覆盖 PC 版本。
- 生成时使用服务端固定的已确认版本；如果用户预期的版本不匹配，拒绝重新确认，避免“看着旧人设，却用新人设生成”。
- 世界书 A→B→A 受激活深度/已访问集合限制，编译完成；输出明确列出 A、B 的激活与裁剪原因。
- 若同时开启概率触发，seed 相同的重试能得到相同 Prompt 结构。

**发现**：角色更新不能通过简单 JSON 覆写；Prompt Compiler 必须独立、确定性并保留 provenance。

## S3：Swipe + 编辑旧消息 + 多角色群聊

- 对 H10 的 AI 回复 A11 重新生成 B11：A11 不删除，B11 与 A11 为同组候选。
- 用户选 B11 继续产生 C12：旧分支指向 A11 的历史仍完整保留。
- 修改更早的用户消息 U8：新节点 U8' 和派生分支，旧 U8 下游不变。
- 群聊发言由明确 speaker 策略决定，每个生成保存当时的角色版本。

**发现**：单个 `messages` JSON 数组不可承担 Swipe+fork；消息图和分支指针是数据模型核心。

## S4：生成中刷新，最终审核拒绝

- 用户刷新页面，SSE 中断；服务端仍知 run_id，前端重新打开只查询 R1 状态，不创建第二次上游请求。
- 模型已输出临时正文，但最终安全拒绝：客户端删除临时输出，不写正式消息节点。
- 根据公示政策，正常安全拒绝的费用由平台承担，冻结释放；运营侧保留非敏感事件和真实成本。

**发现**：SSE 的 delta 不等于完成；安全结果必须参与最终消息提交门槛。

## S5：上游实际消耗，最终 usage 丢失

- 不得将预估 Token 直接当作实际用量向用户隐式扣款。
- 标记 R1=`unknown_usage`；由对账任务查询已知可查询账单，无法恢复时按约定让平台承担/撤销冻结并记录成本异常。
- R1 不得在自动重试时重复发送给模型。必须出现运维告警，以便监测异常次数。

**发现**：需要单独的 `unknown_usage` 终态和人工/自动对账工具，不能只有 success/error 两态。

## S6：支付宝并发通知 10 次

- 同一个 `merchant_trade_no` 的合法签名通知并发到达 10 次，只有一个事务完成订单 paid 和 ledger credit。
- 如通知金额或主体不符，拒绝确认，保留异常事件；不信任前端支付成功跳转。
- 退款重复通知由相同退款唯一键去重。

**发现**：钱包业务必须使用数据库唯一约束和短事务；单靠 JS 的 if 判断不够。

## S7：断电/旧设备恢复/用户删除

- 用户删除会话：服务端写 tombstone 和同步日志；设备 B 一周后上线先拉取删除，不得将旧缓存再次上传。
- 数据库损坏：按已测的加密异地备份恢复，并通过支付提供商查询未对账订单；不能只回滚积分账本而忽略支付已发生的事实。

**发现**：版本游标、删除墓碑、财务补账与备份恢复必须统一演练。

## S8：高峰长上下文 + 3 Mbps 出网

- 一次 1MB Prompt 从 ECS 发往 DeepSeek，仅按 3Mbps 理想上限需要约 2.7 秒出网（未计 TLS/网络延迟）；同时多个请求会竞争带宽。
- 设计要求：Prompt 预算、单次请求体上限、单用户和全站并发上限、队列/背压，角色头像和静态资源缓存，消息按页加载。
- 必须用真实同规格环境实测延迟、网络占用、内存峰值，不能从理论算式承诺支持几十或几百个实时聊天用户。

**发现**：3Mbps 不直接否定文本酒馆，但极长上下文上传可能比生成回复更费带宽。

## 推演后的架构修订摘要

1. 引入 `ContextSnapshot`（带引用的实体版本、摘要 digest），而不只把 Prompt 字符串存在日志里。
2. 引入 `GenerationRun` 状态机与清理/对账 Worker。
3. 把钱包冻结和生成/保存拆成多个短事务。
4. 引入消息图、分支 CAS 和同步 tombstone。
5. 预算估算、世界书命中、记忆引用向用户可解释。
6. 管理员无法默认浏览私聊正文，支付账本与聊天删除周期分离。
7. 备份必须异地加密并演练；部署前确认监管与支付的真实准入状态。
